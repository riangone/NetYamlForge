# 改善ワークフロー（人/AI 共通）

## 1. 基本方針

- 大きな変更は分割し、1タスク1目的で進める。
- 「設計意図」「変更理由」「検証結果」を必ず残す。
- 既存挙動を壊す可能性がある変更は、先に回帰手順を定義する。

## 2. 標準プロセス

1. RFC 作成
2. タスク分解
3. 実装
4. 検証
5. PR 提出
6. レビュー/修正
7. マージ

## 3. RFC（必須）

### 3.1 必須記載項目

1. 背景
2. 現状課題
3. 目標（定量）
4. 変更範囲（対象ファイル/対象機能）
5. 非対象範囲（やらないこと）
6. リスクと回避策
7. 検証方法
8. ロールバック手順

### 3.2 スキップ可能条件

- 1ファイル以内の軽微修正で、かつ挙動影響が局所的な場合のみ。

## 4. タスク分解ルール

1. 1タスクは原則 `<= 1日` で完了可能な粒度にする。
2. 1PRの核心差分は原則 `<= 400行`。
3. 依存タスクは順序を明記する。
4. 不確実性が高い作業は検証タスクを先に切る。

## 5. ブランチ/PR運用

### 5.1 ブランチ命名

- `feat/<area>-<topic>`
- `fix/<area>-<topic>`
- `refactor/<area>-<topic>`
- `test/<area>-<topic>`

### 5.2 PR必須項目

1. 目的
2. 主な変更点
3. 影響範囲
4. リスク
5. 検証結果（実行コマンド + 結果要約）
6. 未対応事項
7. ドキュメント影響（`Documentation impact`）と更新対象

## 6. レビュー観点

1. 仕様逸脱がないか
2. 後方互換性を維持しているか
3. 障害時の診断情報が残るか
4. テスト/回帰観点が不足していないか
5. 可読性と責務分離が維持されているか

## 7. 週次運用

1. 月曜: 今週タスク確定（最大5件）
2. 水曜: 中間レビュー（阻害要因排除）
3. 金曜: 完了判定と次週計画

## 8. 例外運用（緊急障害）

1. 先に復旧を優先
2. 復旧後24時間以内に事後RFC作成
3. 同種障害の再発防止タスクを次スプリントへ投入
