结合 `.NET Core / C#` 技术栈，我将以**企业级架构设计**的视角，为你输出无代码的方案。核心目标是：**让 AI 负责“听懂与引导”，让 .NET 系统负责“校验、决策与持久化”，确保对话自然、数据准确、系统可控**。

---
## 🧭 一、核心设计哲学（架构底线）
1. **AI 无状态，系统有状态**：大模型本身不维护会话上下文，所有状态由 `.NET 服务 + Redis` 管理。AI 仅作为“推理引擎”接收 Prompt 返回结构化结果。
2. **对话驱动状态机，状态驱动业务动作**：用有限状态机（FSM）管控试驾收集流程（如 `INIT → COLLECT_MODEL → COLLECT_CONTACT → CONFIRMING → BOOKING`），防止 AI 跑题或漏字段。
3. **强校验前置，AI 不直连 DB**：AI 输出必须经过 `.NET 层 Schema 校验 + 业务规则校验`，且必须经过用户“显式确认”后才触发事务写入。
4. **工具调用（Tool Calling）为桥**：利用 LLM 原生支持的 Function/Tool Calling 机制，将 AI 意图映射为 .NET 服务方法，实现“自然语言 → 结构化调用”的安全转换。

## 🏗️ 二、系统分层架构（.NET 生态映射）
```
[客户端] (Web/小程序/App)
   │ WebSocket / SSE 实时双工通信
   ▼
[接入网关层] (ASP.NET Core YARP / API Gateway)
   ├─ 身份鉴权 (JWT)
   ├─ 限流熔断 (Polly)
   └─ 路由分发
   │
   ▼
[AI 编排服务] (核心层)
   ├─ 会话上下文管理 (Redis + 滑动窗口)
   ├─ Prompt 模板引擎 (配置化/版本化)
   ├─ 对话状态机 (Stateless / 自研枚举机)
   ├─ Tool 路由与输出校验 (JSON Schema + FluentValidation)
   └─ 降级与人工接管策略
   │
   ▼
[业务服务层] (Domain Services)
   ├─ 试驾档期服务 (排期冲突检测)
   ├─ 预约服务 (事务边界、幂等控制)
   ├─ 客户画像服务 (CRM 同步、标签打标)
   └─ 通知服务 (异步消息队列)
   │
   ▼
[数据与基础设施]
   ├─ 关系型 DB (SQL Server / PostgreSQL + EF Core/Dapper)
   ├─ 缓存/会话 (Redis Cluster)
   ├─ 消息队列 (RabbitMQ / Azure Service Bus / Kafka)
   └─ 对象存储 (审计日志、通话录音、Prompt 版本)
```

## 🔄 三、试驾场景：AI 接待 → 信息入库 核心链路设计
### 1. 会话初始化
- 客户端建立 WebSocket 连接，网关生成 `SessionId`，Redis 初始化会话状态为 `INIT`，加载默认欢迎 Prompt。
- 历史对话按 `SessionId` 分片存储，设置 TTL（如 24h），超限自动归档。

### 2. 多轮意图收集（状态机驱动）
- 用户输入 → AI 编排服务追加至上下文 → 调用 LLM。
- LLM 根据当前状态匹配 Prompt 模板，**仅允许调用当前阶段允许的 Tool**（如 `COLLECT_MODEL` 阶段不可调用 `SAVE_BOOKING`）。
- LLM 返回结构化字段或继续提问。若字段缺失/格式异常，.NET 层拦截并让 AI 重新追问。

### 3. 强校验与确认闸门
- 当状态机进入 `CONFIRMING`，.NET 层组装提取信息，生成摘要 Prompt 让 AI 向用户展示。
- 用户回复“确认” → 触发 `ValidateAndBook` Tool 调用。
- .NET 业务层执行：
  - 手机号正则/运营商校验
  - 驾照类型枚举校验
  - 档期并发冲突检测（Redis 分布式锁 + DB 唯一索引）
  - 合规同意书标记校验
- 校验通过 → 开启 DB 事务写入 → 提交后投递消息至 MQ → 返回成功标识给 AI。
- 校验失败 → 返回明确错误码，AI 针对性引导用户修正（如“该时段已满，请调整时间”）。

### 4. 异步后置动作
- 消息队列消费者触发：短信/企微通知、CRM 客户建档、试驾车辆调度单生成、数据埋点上报。
- 全程可追溯，支持对账与重试。

## 🛠️ 四、关键架构模式与 .NET 技术选型建议
| 关注点 | 架构模式 / 设计策略 | .NET 技术栈建议 |
|--------|-------------------|----------------|
| **AI 集成抽象** | 统一 AI 客户端接口，支持供应商切换（DashScope/OpenAI/本地模型） | `Microsoft.Extensions.AI` (官方新抽象) 或 `Semantic Kernel` |
| **状态管理** | 有限状态机管控对话阶段，防跳跃/死循环 | `Stateless` 库 或 基于 Redis Hash 的自定义状态机 |
| **工具调用路由** | Tool Definition → JSON Schema → C# 强类型方法映射 | 自定义 `ToolRouter` + `System.Text.Json` 序列化 |
| **数据校验** | 输入清洗 + 输出 Schema 校验 + 业务规则校验 | `FluentValidation` + `JsonSchema.Net` + DB `CHECK` 约束 |
| **并发与幂等** | 防止重复预约/重复入库 | Redis 分布式锁 (`RedLock`) + DB 唯一索引 `(phone, preferred_time)` + 请求 `Idempotency-Key` |
| **异步解耦** | 预约成功后通知/归档不阻塞主流程 | `BackgroundService` + `MassTransit` / `RabbitMQ.Client` |
| **弹性与容错** | AI 接口超时/限流/抖动 | `Polly` (重试、熔断、超时、降级策略) |

## 🛡️ 五、数据一致性与安全合规设计
1. **PII 合规处理**：
   - 日志/监控中手机号自动脱敏（`133****5678`）
   - DB 敏感字段加密存储（Always Encrypted 或应用层 AES-GCM）
   - 明确告知用户数据用途，保留授权时间戳
2. **Prompt 安全**：
   - 系统 Prompt 硬编码+配置中心双备份，防客户端注入
   - 输入过滤层拦截恶意指令/越权试探
   - 输出置信度阈值：低于阈值强制转人工
3. **事务边界清晰**：
   - AI 仅生成“意向数据”，.NET 服务执行最终写入
   - 采用 Outbox Pattern 确保 DB 提交与消息投递原子性
   - 提供预约撤销/修改 API，状态机支持 `CANCELLED / MODIFIED`

## 📊 六、容错、降级与可观测性
| 场景 | 架构应对策略 |
|------|-------------|
| **AI 响应超时** | Polly 设置 8s 超时 → 触发缓存兜底回复 → 提示“网络延迟，已为您转接人工” |
| **连续 2 次提取失败** | 状态机标记 `ESCALATE` → 推送会话至人工坐席队列（WebSocket 转发） |
| **大模型服务宕机** | 降级为传统表单引导 + 短信链接，保障核心业务不中断 |
| **可观测性指标** | `token_usage`、`tool_call_success_rate`、`state_transition_latency`、`fallback_rate`、`db_commit_success_rate` |
| **追踪与审计** | OpenTelemetry 全链路透传 `SessionId` → 关联 Prompt 版本、AI 响应、DB 操作日志 |

## 🚀 七、落地演进路线（建议分三期）
1. **Phase 1（MVP）**：单车型试驾预约 → 状态机 + Tool Calling → 校验 → DB 写入 → 短信通知。跑通“对话→结构化→入库”闭环。
2. **Phase 2（增强）**：接入档期实时查询 → 多车型/多版本对比引导 → 人工无缝接管 → Prompt 版本管理 & A/B 测试 → 监控大盘。
3. **Phase 3（智能）**：RAG 接入车型手册/金融政策 → 客户意图预测 → 自动跟进策略（企微/短信） → 销售转化归因分析。
