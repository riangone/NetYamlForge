## 🛠️ 二、 深度契合 NetYamlForge 的改进设计

### 2.1 状态机 (FSM) 与现有对话管理融合
- **不推翻重写**：保留 `SlotFillingManager` 的槽位收集逻辑，将其封装为 FSM 的 `State` 载体。
- **多租户隔离**：状态 Key 必须携带项目前缀  
  `nyforge:{ProjectName}:fsm:{ConversationId} → {State, CollectedSlots, UpdatedAt}`
- **防脱线机制**：增加 `ESCALATE` 状态。当 AI 连续 2 次意图识别置信度 `<0.6`，自动切换至 YAML 定义的 `quick_replies` 表单，并通过 `SignalR` 推送人工坐席队列。

### 2.2 Tool Calling 与动态实体引擎安全对接（核心）
AI 输出必须经过**三重安全网关**才允许执行：
```
LLM Tool Output
    │
    ├─ [1] JsonSchema.Net 结构校验（必填字段/类型/枚举）
    ├─ [2] EntityMetadata 白名单校验（entity/action 必须匹配 projects/*/entities/*.yml）
    ├─ [3] SqlSafetyGuard 标识符过滤（杜绝动态拼接表名/列名）
    │
    ▼
路由至 DynamicEntityCommandService (Insert/Update)
    │
    ▼
触发 IEntityHook 链（validate_phone → audit_log → update_count）
```
- **试驾场景映射示例**：
  AI 调用 `create_test_drive` → 映射至 `service_appointments` 实体 → 框架自动生成参数化 `INSERT` → 执行前自动触发 `validate_phone` 钩子 → 成功后触发 `afterCreate` 钩子写入审计日志并投递通知队列。

### 2.3 缓存与降级策略：轻量优先，按需扩展
- **Phase 1 不强制引入 Redis**：框架 SQLite (WAL模式) 在单店/区域部署下完全可承载会话状态。采用 `MemoryCache` + SQLite 归档即可。
- **Redis 作为可选插件**：仅在 `appsettings.json` 配置 `"Redis:ConnectionString"` 时激活缓存层。未配置时，`ConversationManager` 自动降级为纯 SQLite 查询，保持框架“开箱即用”哲学。
- **Key 命名规范**：`{ProjectName}:ai:session:{Id}:messages` (List) / `:fsm` (String) / `:slots` (Hash)

### 2.4 Prompt/Tool 配置与框架热重载对齐
- **统一配置源**：将 `skills/auto-dealer/` 纳入现有 `YamlHotReloadService` 监视路径。
- **版本路由逻辑**：
  ```csharp
  // 新会话按 SessionId 哈希分配版本，旧会话保持内存隔离
  var version = _hotReloadCache.ResolveVersion(sessionId); 
  var prompt = _promptLoader.Load($"auto-dealer/{version}/_system-prompt-customer.md");
  ```
- **AB 测试**：无需额外路由层，直接复用框架 `ProjectConfig` 的 `features.ai.abTest` 字段，通过 `HotReload` 动态下发流量比例。

### 2.5 钩子系统赋能 AI 数据流转
充分利用 `NetYamlForge` 的钩子生态，实现 AI 与业务解耦：
| 钩子时机 | 职责 | 示例配置 |
|----------|------|----------|
| `beforeCreate` | PII 自动脱敏 + 必填校验 | `validate_phone:Phone` + `trim:CustomerName` |
| `afterCreate` | 异步通知 + 状态同步 | `webhook:https://sms-gateway/notify` + `update_count:sales_leads,ai_touch_count,+1` |
| `afterUpdate` | 档期冲突回滚标记 | 若档期已满，更新状态为 `CONFLICT_RESOLVED` 并记录日志 |

| 阶段 | 原方案重点 | 改进建议（贴合框架） |
|------|-----------|---------------------|
| **Phase 1**<br>(生产就绪) | FSM + Tool校验 + Polly + 档期检测 | ✅ 优先打通 `AIController → ToolValidator → DynamicCrudRepository` 链路<br>✅ Polly 直接注入 `ILlmProvider` 工厂<br>✅ 档期冲突使用 `DB唯一索引(type, date, time) + INSERT OR IGNORE` |

## 🛡️ 四、 关键风险与生产级应对

| 风险场景 | 影响 | NetYamlForge 适配方案 |
|----------|------|----------------------|
| **LLM 幻觉/格式漂移** | 脏数据入库、越权操作 | 强制 `response_format: {type: "json_object"}` + `JsonSchema.Net` 二次校验 + 失败重试(≤2次) + 最终兜底转人工 |
| **高并发档期冲突** | 重复预约、客户投诉 | SQLite WAL 模式 + `INSERT OR IGNORE` + 唯一索引 `(appointment_type, preferred_date, preferred_time)`；Redis 分布式锁仅用于极端峰值 |
| **Prompt 热重载中断会话** | 用户体验断裂、逻辑错乱 | 版本路由基于 `SessionId` 哈希；热重载仅更新内存缓存，**不中断进行中会话** |
| **CLI 工具生产不可靠** | 响应延迟、进程僵死 | 开发环境保留 CLI；生产环境通过 `CliFirstLlmProvider` 自动降级至 HTTP API 直连模式（Ollama/DashScope），Polly 熔断隔离 |
