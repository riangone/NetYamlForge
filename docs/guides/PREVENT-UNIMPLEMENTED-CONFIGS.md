# 防止“定义未实现”问题的防错机制说明

## 1. 问题的本质
在声明式框架（如 NetYamlForge）中，YAML 配置文件是“意图”，而 C# 代码是“执行”。当意图与执行脱节时，系统就会出现静默失败（如按钮点击无效）。

为了彻底杜绝此类问题，本框架设计了两道防线。

---

## 2. 第一道防线：静态代码生成 (Scaffolding)
**目标**：消除手动创建类、接口实现和方法匹配的体力劳动和人为错误。

- **核心工具**：`--scaffold-missing-hooks`
- **工作原理**：
    - 工具会解析所有 YAML 实体文件。
    - 利用反射扫描 `IEntityHook` 和 `IActionHandler` 的现有实现。
    - 发现缺口后，自动生成标准的 `.cs` 代码桩。
- **使用建议**：将此命令视为“保存 YAML 后的必经步骤”。

---

## 3. 第二道防线：运行时动态验证 (Validation)
**目标**：确保即使在忽略了生成步骤的情况下，系统也能感知并报错。

- **核心组件**：`YamlConfigStartupValidator`
- **工作原理**：
    - 应用启动时，在依赖注入完成后执行。
    - 它会检查容器中是否存在所有 YAML 所需的处理器。
    - **反馈机制**：
        - 控制台实时警告：`[WARN] unimplemented_hook ...`
        - 汇总报告：`yaml_config_summary` 显示总缺失数。
- **使用建议**：在 CI/CD 环境中，可配置为“若存在缺失实现则强制退出（Exit 1）”，从而实现强约束。

---

## 4. 针对 AI 协作的特别优化
通过在 `GEMINI.md` 中注入这些规则，任何新的 AI 代理在进入本项目时都会：
1.  **感知能力**：知道 YAML 修改必须配合代码生成。
2.  **验证意识**：知道查看日志中的 `yaml_config_warn` 作为任务完成的判准。
3.  **一致性维护**：即使是不同厂商的 AI，也会遵循同样的 `MissingHooks.cs` 组织模式。

---

## 5. 总结
**YAML 定义 = 契约**
**C# 代码 = 履约**

通过 **Scaffolding (主动生成)** 和 **Validator (被动检查)** 的结合，我们构建了一个自愈式的开发环境，确保 NetYamlForge 的业务逻辑始终完整可用。
