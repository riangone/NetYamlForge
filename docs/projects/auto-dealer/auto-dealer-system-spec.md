## 1. システム概要

- **システム名**：自動車ディーラー統合管理システム
- **目的**：新車・中古車販売、サービス・整備、部品販売、顧客管理、在庫管理、会計・請求を一元管理し、業務効率と顧客満足度の向上を図る
- **対象ユーザー**：販売担当、サービス・整備担当、部品担当、受付、経理・管理部門、管理者
- **利用環境**：Webブラウザ（PC・タブレット対応）、必要に応じて店頭端末

## 2. 主な機能一覧

1. **顧客管理**
   - 顧客基本情報（氏名、連絡先、車両所有歴など）の登録・更新
   - 顧客別の販売・サービス履歴の参照
   - 顧客区分（見込み客、契約済み、リピーターなど）の管理

2. **車両在庫管理**
   - 新車・中古車の在庫登録（車種、グレード、年式、走行距離、価格など）
   - 在庫一覧表示、検索・絞り込み（車種、価格帯、年式など）
   - 入庫・出庫（納車・売却）の履歴管理

3. **販売管理**
   - 見積書作成（車両、オプション、下取り、ローン条件など）
   - 契約書作成・管理（顧客情報、車両情報、支払条件）
   - 納車管理（納車日、納車確認、車検・登録手続きの進捗）

4. **サービス・整備管理**
   - サービス受付（予約・当日受付）
   - 作業指示書作成（作業内容、必要部品、作業時間、担当者）
   - 作業進捗管理（受付→作業中→完了→納車）
   - 点検・整備履歴の記録（次回点検時期の自動算出）

5. **部品管理**
   - 部品在庫登録（部品コード、名称、在庫数、発注点、仕入価格など）
   - 部品発注・入荷管理（発注、入荷確認、在庫更新）
   - 部品使用履歴（サービスでの使用記録）

6. **会計・請求管理**
   - 販売・サービス・部品販売の請求書作成
   - 入金管理（入金登録、未入金一覧）
   - 売上集計（日次・月次、部門別、担当者別）

7. **レポート・分析**
   - 販売台数・売上レポート
   - サービス売上・作業実績レポート
   - 顧客別売上・リピート率分析

8. **マスタ管理**
   - 車種マスタ、グレードマスタ、部品マスタ、顧客区分マスタなどの管理
   - ユーザー権限管理（販売担当、サービス担当、管理者など）

## 3. 画面構成

- **ログイン画面**：ユーザーID／パスワード入力
- **ダッシュボード**：本日の予約件数、未処理の受付、在庫状況、売上概要
- **顧客管理画面**：顧客一覧、検索、新規登録、詳細表示（所有車両・履歴）
- **車両在庫管理画面**：新車・中古車在庫一覧、検索、新規登録、入出庫履歴
- **販売管理画面**：見積書作成、契約書作成、納車管理、販売履歴一覧
- **サービス・整備管理画面**：受付・予約一覧、作業指示書作成、作業進捗管理、履歴参照
- **部品管理画面**：部品在庫一覧、発注・入荷管理、使用履歴
- **会計・請求画面**：請求書作成、入金管理、売上集計レポート
- **レポート・分析画面**：各種レポートの表示・出力（CSV/PDF）
- **設定画面（管理者用）**：マスタ管理、ユーザー権限設定、システム設定

## 5. 制約・前提条件

- 社内ネットワークからのみアクセス可能（必要に応じてVPN経由）
- ユーザーは事前に管理者によって登録され、権限に応じた操作制限がかかる
- 顧客情報・車両情報は個人情報を含むため、アクセス権限を厳格に管理
- 車検・登録手続きの進捗は、外部システムや手動入力で連携可能（必要に応じて）
- 在庫数・部品数はリアルタイム更新を基本とし、二重販売・在庫不足を防止

---

## 6. 非機能要件

| 項目 | 要件 |
|------|------|
| 性能 | 在庫照会・顧客検索は2秒以内、請求書作成は3秒以内 |
| 可用性 | 営業時間中（8:00–20:00）は原則停止なし |
| セキュリティ | ログインなしでは一切閲覧不可、顧客情報・車両情報の暗号化保存、操作ログの記録 |

## 7. 販売契約フロー詳細仕様

### 7.1 フロー概要

見込み顧客の情報登録から、見積・契約・納車・アフターフォローまでの一連の流れを管理する。新車・中古車の両方に対応。

### 7.2 画面遷移

```
ダッシュボード
  → 顧客管理画面（新規登録／既存検索）
    → 車両在庫管理画面（車両選定）
      → 見積書作成画面
        → 見積書確認画面（プレビュー）
          → 顧客管理画面（見積履歴登録）
            → 契約書作成画面
              → 契約書確認画面（プレビュー）
                → 入金管理画面
                  → 納車準備管理画面
                    → 納車確認画面
                      → アフターフォロー画面
```

### 7.3 ステップ詳細

1. **顧客情報登録／照会**
   - 新規顧客：氏名、連絡先、住所、希望車種などを登録
   - 既存顧客：顧客IDまたは氏名で検索し、過去の購入履歴・サービス履歴を参照

2. **車両選定・見積作成**
   - 在庫車両またはカタログ車種から選択
   - オプション、保険、ローン条件、下取り条件などを含めた見積書を自動生成
   - 見積書はPDF出力可能

3. **見積提示・交渉**
   - 見積書の改訂履歴を管理（複数回の見積に対応）
   - 交渉メモ（顧客の要望、価格交渉内容など）を記録

4. **契約書作成**
   - 見積内容を基に契約書を作成（契約番号自動採番）
   - 契約書に顧客署名欄を設け、紙または電子署名で管理

5. **入金・ローン手続き**
   - 頭金・中間金・残金の入金管理
   - ローン契約の場合は金融機関との連携情報（申込日、承認日など）を記録

6. **納車準備**
   - 車検・登録・納車前点検の進捗を管理
   - 納車日時の予約をシステム上で管理

7. **納車**
   - 納車確認（顧客への引き渡し完了）を記録
   - 納車時点で在庫ステータスを「納車済み」に更新

8. **アフターフォロー**
   - 納車後1週間・1か月などのフォローアップタスクを自動生成
   - 顧客満足度アンケートの実施状況を記録

## 8. サービス受付フロー詳細仕様

### 8.1 フロー概要

顧客からのサービス予約・受付から、作業指示・部品使用・請求・納車までの一連の流れを管理する。定期点検、修理、車検などに対応。

### 8.2 画面遷移

```
ダッシュボード
  → サービス受付画面（予約／当日受付）
    → 顧客・車両照会画面
      → 作業指示書作成画面
        → 作業指示書確認画面
          → 作業進捗管理画面
            → 部品使用登録画面
              → 請求書作成画面
                → 入金管理画面
                  → 納車確認画面
                    → サービス履歴画面
```

### 8.3 ステップ詳細

1. **受付・予約**
   - 顧客IDまたは車両情報で検索し、過去のサービス履歴を参照
   - 予約受付：希望日時、作業内容（点検、修理、車検など）を入力
   - 当日受付：受付時刻と作業内容を登録

2. **作業指示書作成**
   - 作業内容を詳細に記録
   - 必要部品をリストアップし、在庫から自動引当
   - 作業時間の見積もりを設定

3. **作業進捗管理**
   - ステータス管理：受付済み→作業中→完了→納車待ち→納車済み
   - 担当者（整備士）の割り当て
   - 作業開始・終了時刻を記録

4. **部品使用・在庫更新**
   - 作業中に使用した部品を実績として登録
   - 在庫数から自動減算
   - 部品不足時は発注フラグを立てる

5. **請求書作成**
   - 作業料金＋部品代金＋消費税を自動計算
   - 請求書を発行（PDF出力可能）

6. **入金・納車**
   - 入金確認後、納車処理を実施
   - 顧客への車両引き渡しを記録

7. **履歴管理**
   - 次回点検時期を自動算出（走行距離・日数ベース）
   - 顧客別・車両別のサービス履歴を一覧表示

## 9. 部品在庫管理フロー詳細仕様

### 9.1 フロー概要

部品の入庫・出庫・在庫数・発注を一元管理し、在庫切れや過剰在庫を防止する。

### 9.2 画面遷移

```
ダッシュボード
  → 部品在庫一覧画面
    → 部品詳細画面
    → 部品入庫登録画面
    → 部品出庫登録画面
    → 部品発注画面
      → 発注履歴画面
    → 在庫調整画面
      → 在庫調整履歴画面
```

### 9.3 ステップ詳細

1. **部品マスタ登録**：部品コード、名称、仕入価格、販売価格、メーカー、在庫数、発注点、安全在庫数を登録

2. **入庫管理**：発注した部品の入荷を確認し、在庫数を更新。入荷伝票番号、入荷日、数量、単価を記録

3. **出庫管理**：サービスでの使用、販売などによる出庫を記録。出庫時に在庫数から減算

4. **在庫照会・検索**：部品コードや名称で検索。在庫数が発注点を下回った場合、アラート表示

5. **発注管理**：発注点を下回った部品を一覧表示し、発注リストを作成。発注先、発注数量、希望納期を設定

6. **在庫調整**：棚卸しによる実在庫とシステム在庫の差異を調整。調整理由を記録

7. **レポート**：在庫回転率、在庫金額、発注頻度などのレポートを出力

## 11. 内部業務処理詳細

### 11.1 販売契約フロー

#### 顧客情報登録処理

- **入力**：顧客基本情報（氏名、連絡先、住所、顧客区分など）
- **処理**
  - 顧客IDを自動採番（例：CUST-YYYYMMDD-連番）
  - 氏名・電話番号・メールアドレスのフォーマットチェック
  - 重複登録チェック（同一電話番号・メールアドレス）
- **データ更新**：顧客テーブルに新規レコードを挿入。登録日時をシステム日時で設定

#### 見積書作成処理

- **入力**：顧客ID、車両ID、オプション、下取り情報、ローン条件など
- **処理**
  - 見積番号を自動採番（例：EST-YYYYMMDD-連番）
  - 車両の在庫ステータスが「在庫」かチェック（売約済みならエラー）
  - 見積金額の自動計算：車両基本価格 ＋ オプション合計 ＋ 保険料 − 下取り価格 ＋ 消費税
- **データ更新**：見積テーブルに新規レコードを挿入

#### 契約書作成処理

- **入力**：見積ID、契約日、契約金額、支払方法、頭金、ローン金額、納車予定日など
- **処理**
  - 契約番号を自動採番（例：CNT-YYYYMMDD-連番）
  - 頭金＋ローン金額が契約金額以下かチェック（超過時エラー）
  - 納車予定日が契約日以降かチェック
  - 車両の在庫ステータスを「受注済み」に更新
- **データ更新**：契約テーブルに新規レコード挿入。車両テーブルのステータスを「受注済み」に更新

#### 入金処理

- **入力**：契約ID、入金日、入金金額、入金種別（頭金、中間金、残金など）
- **処理**
  - 入金金額が未入金残高以下かチェック（超過時エラー）
  - 未入金残高を計算：契約金額 − 累計入金金額
- **データ更新**：入金テーブルに新規レコード挿入。全額入金時に契約テーブルのステータスを「入金完了」に更新

#### 納車処理

- **入力**：契約ID、納車日、納車時刻、納車担当者、納車確認フラグ
- **処理**
  - 納車確認フラグが「済」かチェック（未チェック時は保存不可）
  - 車両の在庫ステータスを「納車済み」に更新
  - 顧客のリピートフラグを更新（条件に応じて）
- **データ更新**：納車テーブルに新規レコード挿入。車両テーブルのステータスを「納車済み」に更新

### 11.2 サービス受付フロー

#### サービス受付処理

- 受付IDを自動採番（例：SRV-YYYYMMDD-連番）
- 希望日が当日または未来日かチェック
- 顧客・車両の存在チェック

#### 作業指示書作成処理

- 作業指示書番号を自動採番（例：WO-YYYYMMDD-連番）
- 見積作業時間が1–480分の範囲かチェック
- 必要部品の在庫数チェック（在庫数 > 0）

#### 作業進捗更新処理

- ステータスが「受付済み→作業中→完了→納車済み」の順序かチェック（逆順はエラー）
- 実作業時間を計算（作業終了時刻 − 作業開始時刻）

#### 部品使用登録処理

- 使用部品の在庫数チェック（使用数量 ≤ 現在の在庫数）
- 部品テーブルの在庫数から使用数量を減算
- 在庫数が発注点を下回った場合、発注フラグを立てる

#### 請求書作成処理

- 税込金額を計算：（作業料金 ＋ 部品代金）×（1 ＋ 消費税率/100）
- 請求番号を自動採番（例：INV-YYYYMMDD-連番）

### 11.3 部品在庫管理フロー

#### 部品新規登録処理

- 部品コードの重複チェック
- 発注点 ≥ 安全在庫数かチェック（設定ミス防止）

#### 部品入庫処理

- 部品テーブルの在庫数を増加（現在の在庫数 ＋ 入庫数量）
- 在庫数が発注点以上になった場合、発注フラグを解除

#### 部品出庫処理

- 在庫数チェック（出庫数量 ≤ 現在の在庫数）
- 部品テーブルの在庫数を減少
- 在庫数が発注点を下回った場合、発注フラグを立てる

#### 在庫調整処理

- 調整後の在庫数が0以上かチェック（負にならないように）
- 調整理由（破損、紛失など）を記録

- 1つの業務処理を1トランザクションとして扱う
- トランザクション境界：処理開始時に開始、全更新成功時にコミット、いずれかの更新失敗時にロールバック

| ロールバック条件 | いずれかのテーブル更新失敗時 |
| コミット条件 | 両テーブルの更新成功時 |

| 項目 | 詳細 |
|------|------|
| 更新対象テーブル | 入金テーブル（挿入）、契約テーブル（ステータス更新） |
| ロールバック条件 | いずれかのテーブル更新失敗時、入金金額超過時は事前エラー |

#### 納車処理

| 項目 | 詳細 |
|------|------|
| 更新対象テーブル | 納車テーブル（挿入）、車両テーブル（更新）、顧客テーブル（更新） |
| ロールバック条件 | いずれかのテーブル更新失敗時 |

### 12.2 サービス受付フロー

#### 部品使用登録処理

| 項目 | 詳細 |
|------|------|
| 更新対象テーブル | 部品使用テーブル（挿入）、部品テーブル（在庫数減算） |
| ロールバック条件 | いずれかのテーブル更新失敗時、在庫不足時は事前エラー |

#### 請求書作成処理

| 項目 | 詳細 |
|------|------|
| 更新対象テーブル | 請求テーブル（挿入）、サービス受付テーブル（請求済みフラグ更新） |
| ロールバック条件 | いずれかのテーブル更新失敗時 |

## 13. バッチ処理（定期実行）

### 13.1 月末在庫集計バッチ

- **実行タイミング**：毎月最終営業日 23:00
- **cron設定**：`0 23 28-31 * * [ -f /path/to/last_business_day.sh ] && /path/to/inventory_summary_batch.sh`
- **処理内容**：部品テーブルから全レコードを取得し、月初在庫数・入庫数・出庫数・月末在庫数を計算して在庫集計テーブルに挿入
- **出力**：在庫集計レポート（CSV/PDF）、在庫回転率
- **リソース制限**：メモリ最大2GB、CPU最大80%、タイムアウト30分
- **アラート閾値**
  - 部分成功：エラー率 ≤ 1%
  - 失敗：エラー率 > 1%、または致命的エラー
  - 実行時間超過アラート：45分超過時

### 13.2 有給休暇自動付与バッチ

- **実行タイミング**：毎月1日 00:00
- **cron設定**：`0 0 1 * * /path/to/paid_leave_grant_batch.sh`
- **処理内容**：全社員の入社日から経過月数を計算し、会社規定に基づく付与日数を算出。有給休暇テーブルに付与レコードを挿入し残日数を更新
- **リソース制限**：メモリ最大1GB、CPU最大60%、タイムアウト15分
- **アラート閾値**
  - 部分成功：エラー率 ≤ 0.5%
  - 失敗：エラー率 > 0.5%

### 13.3 勤怠集計バッチ

- **実行タイミング**：毎月1日 00:00（前月分）
- **cron設定**：`0 0 1 * * /path/to/attendance_summary_batch.sh`
- **処理内容**：勤怠テーブルから前月分のレコードを取得し、個人別・部署別の総労働時間・残業時間・遅刻回数を集計
- **リソース制限**：メモリ最大1.5GB、CPU最大70%、タイムアウト20分
- **アラート閾値**
  - 部分成功：エラー率 ≤ 1%
  - 失敗：エラー率 > 1%

### 13.4 サービス次回点検リマインダーバッチ

- **実行タイミング**：毎日 08:00
- **cron設定**：`0 8 * * * /path/to/service_reminder_batch.sh`
- **処理内容**：サービス履歴テーブルから次回点検時期が1か月以内のレコードを取得し、顧客へリマインダーメール／通知を送信
- **リソース制限**：メモリ最大1GB、CPU最大50%、タイムアウト10分
- **アラート閾値**
  - 部分成功：送信失敗率 ≤ 2%
  - 失敗：送信失敗率 > 2%

### 13.5 ログ出力形式

**テキストログ形式**（出力先：`/var/log/batch/[バッチ名]_YYYYMMDD.log`）

### 14.4 問い合わせ経路ごとの処理フロー

#### 電話受付フロー（スクリプト管理を含む）

1. **電話着信**：CTIシステムから着信情報を受信
2. **顧客情報照会**：発信番号で顧客テーブルを検索。既存顧客は履歴を自動表示
3. **スクリプト表示**：問い合わせ種別に応じて定型スクリプトを表示
   - 例（サービス）：「お電話ありがとうございます。○○自動車でございます。ご用件をお伺いしてもよろしいでしょうか。」
4. **問い合わせ内容入力**：問い合わせ種別・内容・緊急度を入力
5. **サポートチケット作成**：必要に応じてチケットを自動生成
6. **対応完了**：対応内容を記録しステータスを更新

**スクリプト管理テーブル**：スクリプトID、問い合わせ種別、表示順序、スクリプト内容、有効フラグ

#### メール受付フロー（自動取り込み）

1. **メール受信**：IMAP/POP3から新着メールを5分ごとに取得（バッチ処理）
2. **顧客情報照会**：差出人メールアドレスで顧客テーブルを検索
3. **問い合わせ内容解析**：件名・本文のキーワードマッチングで種別を自動分類
   - 例：「点検」「修理」→ サービス問い合わせ、「価格」「見積」→ 販売問い合わせ
4. **サポートチケット自動生成**：優先度：中、ステータス：未対応で自動生成
5. **担当者割り当て**：問い合わせ種別に応じてルールベースで自動割り当て

#### Webフォーム受付フロー

1. 顧客がWebフォームから情報を送信
2. API経由でJSON形式のデータを受信
3. 顧客情報を照会／新規登録
4. サポートチケットを自動生成し担当者を割り当て

### 14.5 営業活動のKPI設定

| KPI | 計算式 |
|-----|--------|
| リードコンバージョン率 | 成約リード数 ÷ 総リード数 × 100（%） |
| 商談成約率 | 成約商談数 ÷ 総商談数 × 100（%） |
| フォローアップ達成率 | 実施済みフォローアップ数 ÷ 総フォローアップ数 × 100（%） |
| 問い合わせ対応時間 | 総対応時間 ÷ 解決済み問い合わせ数 |
| サポートチケット解決率 | 解決済みチケット数 ÷ 総チケット数 × 100（%） |
| 顧客満足度 | 総スコア ÷ 回答数（1–5点スケール） |

### 14.6 外部ツール連携

#### メールサーバー連携

- **プロトコル**：SMTP（送信）、IMAP/POP3（受信）
- **認証**：OAuth2.0 または ユーザー名／パスワード
- **頻度**：5分ごとのポーリング（受信）、即時送信（送信）

#### SMS連携

- **API連携**：SMSゲートウェイプロバイダ（例：Twilio、Nexmo）のREST APIを利用
- **認証**：APIキー／シークレットトークン
- **用途**：リードフォローアップリマインダー、緊急連絡

#### LINE連携

- **連携方式**：LINE Official Account API
- **認証**：Channel Access Token（OAuth2.0）
- **受信**：LINEメッセージイベントをWebhookで受信し、問い合わせとして登録
- **送信**：リマインダー、アンケート、プロモーション情報をLINEで送信

### 14.7 顧客対応・営業関連バッチ処理

#### 顧客満足度アンケート送信バッチ

- **実行タイミング**：毎日 09:00（前日対応済みチケット対象）
- **処理内容**：前日完了チケットの顧客へアンケートメールを自動送信
- **アラート閾値**：送信失敗率 > 5% で警告

#### リードフォローアップリマインダーバッチ

- **実行タイミング**：毎日 08:00
- **処理内容**：本日予定のフォローアップタスクの担当者へリマインダー送信
- **アラート閾値**：送信失敗率 > 5% で警告

#### 未対応問い合わせエスカレーションバッチ

- **実行タイミング**：毎日 10:00
- **処理内容**：受付後24時間以上未対応の問い合わせを抽出し、管理者へエスカレーション通知
- **アラート閾値**：エスカレーション件数 > 10件で警告

## 15. AI窓口システム設計（将来像）

### 15.1 システム概要

- **目的**：AIが一次窓口として顧客対応（問い合わせ、サポート、営業の初期対応）を担い、人間は例外対応・高難度商談に集中する
- **対象業務**：問い合わせ受付、FAQ回答、サービス予約、見積もり・商談の初期対応、フォローアップ
- **利用環境**：Webチャット、音声通話（IVR＋AI）、メール、SMS、LINE、店頭タブレット

### 15.2 主な機能一覧

1. **マルチチャネルAI対応**：Webチャット、音声通話、メール、SMS、LINEからの問い合わせをAIが統一処理
2. **自然言語理解（NLU）**：顧客の意図（インテント）を自動分類
3. **コンテキスト管理**：対話履歴、顧客プロファイル、車両情報を保持し文脈を理解した応答を生成
4. **自動提案・推奨**：顧客のニーズに応じた車種提案、サービスプラン提案を自動生成
5. **自動フォローアップ**：商談中リードへのリマインダー、アンケート送信
6. **エスカレーション管理**：AI解決不能な場合、人間担当者へ自動転送
7. **学習・改善ループ**：対話ログ分析、AIモデルの継続学習、人間フィードバック取り込み

### 15.6 AIモデルのトレーニングパイプライン

**全体フロー**
```
データ収集
  → 前処理（クリーニング・ラベル付与・特徴量エンジニアリング）
    → 学習（NLUモデル・対話管理ポリシー・応答生成モデル）
      → 評価（オフライン指標 + A/Bテスト）
        → デプロイ（CI/CDパイプライン）
          → 監視（ドリフト検知・再学習トリガー）
```

**モデル別学習方式**

| モデル | アーキテクチャ | 評価指標 |
|--------|--------------|----------|
| NLUモデル | BERTベースの分類器＋CRFによるエンティティ抽出 | Intent Accuracy、Entity F1-score |
| 対話管理ポリシー | 強化学習（RL）またはルール＋統計的ポリシー | 対話成功率、平均ターン数 |
| 応答生成モデル | GPT系LLM（ファインチューニング） | BLEUスコア、人間評価（満足度） |

**デプロイ**
- CI/CDパイプライン（GitLab CI／Jenkins）
- Kubernetes上のモデルサーバー（TensorFlow Serving／Triton）
- ブルーグリーンデプロイで本番環境へ反映

**監視指標**
- 推論遅延（P95 < 200ms）
- エラー率（< 1%）
- ドリフト指標（データ分布の変化）

### 15.7 A/Bテスト仕組み

**モデルバージョン管理**：MLflowまたは自前のレジストリでモデルID・バージョン・学習日・評価指標を管理

**トラフィック分割**：セッションIDのハッシュ値に基づきモデルを振り分け（例：A:B = 50:50）

**評価指標**

| 指標 | 判定手法 |
|------|----------|
| 成約率 | カイ二乗検定 |
| セッション長（ターン数） | t検定 |
| エスカレーション率 | カイ二乗検定 |
| 顧客満足度スコア | t検定 |

**判定基準**：p-value < 0.05、かつ各モデルで1,000セッション以上のサンプルサイズ

**勝者モデル反映プロセス**
1. A/Bテスト期間（例：2週間）を設定
2. 評価指標を日次でモニタリング
3. 統計的有意に優れたモデルを勝者として選定
4. 勝者モデルを全トラフィックに適用

**ロールバック条件**：エラー率急増、顧客満足度低下などの問題発生時に前バージョンへ自動ロールバック

### 15.8 セキュリティ・プライバシー

- **データ暗号化**：対話ログ中の個人情報（氏名、連絡先等）を暗号化保存
- **アクセス制御**：AIモデル学習用データへのアクセス権限を限定
- **同意管理**：音声録音・対話ログ利用について顧客同意を取得（オプトイン／オプトアウト）
- **監査ログ**：AIの重大な判断（高額契約の自動提案等）については人間の承認を必須とする

### 15.9 将来の拡張ポイント

- **感情分析**：顧客の感情（不満・満足）を音声・テキストから推定し対応を最適化
- **マルチモーダルAI**：画像（車両写真）や動画（故障箇所）をAIが解析し診断支援
- **パーソナライゼーション**：購買履歴・サービス履歴に基づく超個別提案を生成
- **予測分析**：リードの成約確率をAIが予測し、優先度の高いリードを人間に集中配分
- **外部CRM連携**：Salesforce・HubSpotとのデータ双方向同期（リード・商談情報）
- **CTI連携**：着信情報の自動取り込み、スクリプト連動、通話録音の紐付け
