# 12週間改善ロードマップ

## 1. 目的

- 設定駆動 CRUD 基盤を、複数メンバー/複数AIで継続改善できる状態へ移行する。
- 不具合の「事後発見」中心から、起動時・PR時に検出する体制へ移行する。

## 2. KPI（完了判定指標）

- 主要回帰シナリオ成功率: 95%以上
- P1 障害: 月1件未満
- 新規エンティティ初期投入時間: 0.5日以内
- 設定不備の原因特定時間: 10分以内

## 3. フェーズ計画

### Phase 1（Week 1-2）: 基線整備

目的:
- 改善作業の入口を標準化し、作業品質のばらつきを抑える。

実施:
1. 改善計画ドキュメント運用開始（本ディレクトリ）
2. RFC テンプレート運用開始
3. PR テンプレート/レビュー基準を合意
4. 週次定例（進捗・リスク）を固定

成果物:
- 運用テンプレート一式
- 最小品質ゲート運用開始

完了条件:
- 新規PRが全件テンプレート準拠

### Phase 2（Week 3-5）: 設定安全性と型安全性

目的:
- YAML/Hook のランタイム失敗を起動時失敗へ前倒しする。

実施:
1. YAML スキーマ検証強化（必須、型、参照整合）
2. エラー出力の位置情報強化（プロジェクト/エンティティ/キー/行）
3. フィルタ・Hook値の型変換ポリシー統一
4. Hook コンパイル失敗ログに修正ヒント追加

成果物:
- 設定検証レポート
- 型変換共通ユーティリティ

完了条件:
- 設定不備の大半を起動時に検出

### Phase 3（Week 6-8）: 可観測性と診断

目的:
- 問題の再現と根因特定を短時間化する。

実施:
1. 動的クエリ/Hook実行の構造化ログ追加（処理時間、結果、失敗理由）
2. 慢SQL検知（閾値超過ログ）
3. 設定診断ページ追加（最終有効設定の可視化）
4. エラートレースIDの統一

成果物:
- ログ設計ドキュメント
- 設定診断画面

完了条件:
- 不具合調査時間 10分以内を実現

### Phase 4（Week 9-10）: フロント状態整合

目的:
- HTMX 部分更新時の状態ずれを抑止する。

実施:
1. filter/sort/page/picker の状態モデル統一
2. Clear/再検索/戻る動作の共通関数化
3. 同名ID競合の排除（コンポーネントスコープ化）
4. UI回帰シナリオの標準化

成果物:
- 画面状態管理の実装ガイド
- 主要画面の動作統一

完了条件:
- 既知の状態ずれ不具合を解消

### Phase 5（Week 11-12）: テスト自動化とリリース運用

目的:
- 改善後の品質を継続保証できる状態にする。

実施:
1. `NetYamlForge.Tests` 作成
2. 重要経路の統合テスト追加（一覧、フィルタ、ページング、Hook）
3. リリース前チェックリスト運用開始
4. 変更ログ整備

成果物:
- 自動テスト基盤
- リリース判定手順

完了条件:
- リリース前に自動/手動チェックを標準実行

## 4. 優先改善バックログ（Top 10）

1. 設定ローダーの厳格バリデーション
2. Hook コンパイルエラーの詳細化（行番号・提案）
3. 動的SQLの許可列ホワイトリスト強化
4. フィルタ値パース共通化（単一/複数/範囲/日付）
5. picker の要素探索スコープ統一
6. count パラメータ運用の統一
7. 慢クエリログと閾値管理
8. 統合テスト導入
9. 設定診断UI実装
10. ドキュメント更新フローの固定

## 5. 週次レビュー項目

1. KPI 推移
2. 未解決高優先度バグ
3. 次週の作業容量（20%は割り込み対応枠）
4. AI生成PRの品質（差し戻し理由の分類）
